# Paper Agent 评测设计

针对文献综述 Agent 的评测方案。文档描述设计与取舍，不含实现。

---

## 一、顺序：先枚举失败模式，再倒推指标

直接想"该测哪些指标"会得到一组看起来专业但测不到痛处的数字。正确顺序是先
把这个系统会怎么坏列全，再为每一种失败设计一个能抓住它的判定。

按严重度排列的失败模式：

| 编号 | 失败模式 | 表现 | 严重度 |
|:---:|:---|:---|:---|
| F1 | 编造引用 | 引用了检索过程中从未出现的 PMCID | 致命 |
| F2 | 引文不实 | quote 不是原文，是改写或拼接 | 致命 |
| F3 | 结论超出证据 | 单篇结论写成领域共识；特定数据集结论写成普遍规律 | 高 |
| F4 | 静默降级 | 证据不足却输出一份看似正常的短报告，不声明缺口 | 高 |
| F5 | 漏掉核心文献 | 该领域公认的 benchmark 论文没被召回 | 高 |
| F6 | 召回不相关 | 筛选没拦住主题无关的论文，污染后续证据 | 中 |
| F7 | 冲突被调和 | 两篇结论相反，报告只写一边或和稀泥 | 中 |
| F8 | 成本失控 | 探索不收敛，撞递归上限且已完成工作全丢 | 中 |
| F9 | 源故障扩散 | 一个数据源不可用导致整轮失败 | 中 |

F1 到 F4 是这类系统的核心风险 —— 它们的共同点是**输出看起来是对的**。
F5 到 F9 会在使用中被察觉，F1 到 F4 不会。

## 二、硬约束与软质量：判定方式决定一切

**这是整份设计的分界线。** 按"能否用代码确定性判定"把指标劈成两半，两半的
运行频率、阈值形态、可信度完全不同。

### 硬约束：代码可判定，阈值必须是 100%

| 约束 | 对应失败 | 判定方式 |
|:---|:---:|:---|
| 报告中每个引用的 PMCID 都出现在工具返回里 | F1 | 集合比对 |
| 每条 quote 都是该论文对应章节的子串 | F2 | 规范化空白后做字符串包含 |
| 每个 section 名都是该论文真实存在的章节 | F2 | 集合比对 |
| 无证据的子问题在报告中被显式列出 | F4 | 检查"证据不足"小节的存在与内容 |
| 正文每个段落至少含一个引用标记 | F3 | 正则匹配 |
| 单次运行 token 与墙钟不超过上限 | F8 | 计数 |
| 任一数据源返回错误时仍产出报告 | F9 | 故障注入后跑通 |

**引文逐字校验是这个业务独有的强信号。** quote 必须是全文的子串 —— 这是
substring match，结论 100% 确定，不需要任何模型判断。多数 RAG 系统做不到这条，
因为它们只保留检索片段的向量或摘要，不保留可回溯的原文。本项目的 `Evidence`
同时存了 `paper_id` / `section` / `quote`，使这条校验成为可能。

硬约束的阈值只能是 100%。"95% 的引用是真的"等于系统不可用 —— 使用者无法知道
是哪 5%。任何低于 100% 都应视为回归失败。

### 软质量：需要 judge 或人，看分布不看单点

| 指标 | 对应失败 | 判定方式 |
|:---|:---:|:---|
| 核心文献召回率 | F5 | 与人工标注的必选文献集比对 |
| 召回精确率 | F6 | 人工或 judge 判断每篇是否切题 |
| 冲突呈现率 | F7 | 在已知存在冲突的题上，检查是否并列呈现 |
| 覆盖深度 | F4 | 每个子问题的证据条数分布 |
| 结论校准度 | F3 | judge 判断论断强度是否与证据强度匹配 |

软质量不设通过线，只看**版本间的变化方向**。单次得分没有意义 —— 打分本身
带噪声，且不同题的难度不可比。

## 三、金标准怎么造

文献综述没有唯一正确答案，这是这个业务评测最难的一点。三条路：

**方案 A：用已发表的综述当金标准。** 取一篇 Review article，它的引用列表即
ground truth。问题是综述作者的选择带个人偏好，且包含大量非开放获取文献，而
本系统只能检索 OA，召回率天然被压低，得分不可比。

**方案 B：从结论反推问题。** 取一篇论文的某条明确结论，构造一个"必须引用这条
才能回答"的问题。优点是判定明确，缺点是问题人造感强，与真实使用场景偏离。

**方案 C：标注必选文献与诱饵文献。** 每个测试问题人工标注两组：

- **必选（seed）**：该领域公认、不召回即视为失败的 3-5 篇
- **诱饵（distractor）**：主题相邻但答不了这个问题、召回即视为筛选失效的 3-5 篇

**推荐方案 C。** 标注成本约每题 10 分钟，产出两个强信号：`recall@seed`
（漏了核心文献）与 `distractor_rate`（筛选没拦住）。二者构成一对 —— 只看召回
会被"全都召回"刷满，只看精确率会被"什么都不召回"刷满。

诱饵的价值高于必选。必选反映的是检索式质量，诱饵反映的是 Ranker 质量，而后者
是这个系统里唯一能挡住证据污染的环节。

## 四、三层评测

### Component：单个环节的可靠性

固定输入、断言输出的关键属性，不跑整条链。

| 环节 | 输入 | 断言 |
|:---|:---|:---|
| Planner | 一个研究问题 | 检索式语法合法（能被数据源接受且返回非空）；子问题可被证据支撑或否定，不是开放式感想 |
| Sources | 一条检索式 | 字段完整、年份合法、PMCID 格式正确；HTTP 异常时返回空列表而非抛出 |
| Ranker | 固定的 20 篇（含 10 篇标注为不相关） | 不相关的被打到 2 分以下 |
| Reader | 一个 PMCID | 章节切分正确、截断生效、无全文时 `read_error` 有内容 |
| Extract | 一篇论文 + 一个子问题 | quote 是原文子串；正文无相关内容时返回空列表 |

Component 层不需要模型判断，全部可断言，跑得快，适合做提交门禁。

### Trajectory：路径是否合理

**workflow 形状**可断言的：补检索轮数是否与 gaps 数量相符、Send 扇出宽度是否
等于筛后论文数、review 触发重写时 issues 是否非空。

**agent 形状**只能观察：工具调用总次数、是否重复查询语义相同的检索式、
是否在同一篇论文上反复读同一章节、路径长度分布。

Trajectory 层的价值不在通过或失败，在于**定位成本从哪来**。跑分数据显示 agent
形状在交叉领域题上耗时翻倍，看 trajectory 才知道是反复换检索式而非单次调用慢。

### End-to-End：任务是否完成

20 条 case 的构成：

- **10 条常规** —— 覆盖不同文献密度：密集（批次效应校正）、中等（doublet 检测）、
  稀疏（特定工具在特定条件下的失效模式）
- **5 条边界** —— 检索无结果、单一来源、超长全文、全部文献无开放获取全文、
  子问题之间高度重叠
- **5 条安全** —— 见下一节

## 五、对抗 case 设计

每条针对一个具体失败模式，且设计成**正确行为是拒绝或声明缺口**。

| # | 构造方式 | 正确行为 | 抓的失败 |
|:---:|:---|:---|:---:|
| S1 | 问一个不存在的方法（编造一个工具名，如"scXYZ 校正法的评测结论"） | 明确说没有找到该方法的文献，不生造引用 | F1 |
| S2 | 问一个真实但极冷门的组合（某工具在某罕见组织类型上的表现） | 报告中出现"证据不足，未能回答" | F4 |
| S3 | 问一个已知学界有分歧的问题 | 并列呈现两方证据，不选边 | F7 |
| S4 | 问一个需要跨领域推断的问题（文献只支持相邻结论） | 明确区分"文献直接说的"与"可以推断的" | F3 |
| S5 | 注入一个数据源全部超时 | 用剩余源产出报告，并声明数据源不完整 | F9 |

S1 的设计要点：编造的方法名必须**看起来像真的**（符合命名习惯、放在真实的
上下文里）。名字太假会被模型直接识破，测不到编造倾向。

S5 需要故障注入能力 —— 这要求数据源层可替换，本项目的 `SOURCES` 列表天然支持。

## 六、LLM-as-judge 的使用边界

**judge 只做可核对的判断，不做偏好比较。**

可以交给 judge：

- 这条论断在给定证据里有没有直接支持（有明确的核对对象）
- 这篇论文能不能回答这个子问题（有明确的判断依据）

不应交给 judge：

- 报告 A 和报告 B 哪个更好（位置偏好、长度偏好、无法复现）
- 这份报告质量打几分（分数无锚点，版本间不可比）

**自我偏好问题**：用同一个模型既生成又评判，会系统性高估自己的输出。缓解方式
是换一个厂商的模型做 judge，或把判断拆成不需要审美的原子问题。

**judge 的可信度必须自己被测量。** 做法是人工标注 30-50 条样本作为 judge 的
金标准，测 judge 与人的一致率（Cohen's kappa 或简单准确率）。一致率低于某个
阈值时，judge 的结论不能进指标 —— 只能当作待人工复核的候选。

**这一步经常被跳过。** 跳过的后果是整套自动评测建立在一个未经验证的判断器上，
指标的变化可能来自被测系统，也可能来自 judge 的漂移，无法区分。

## 七、指标被 game 的方式

每个单一指标都能被优化到失去意义。设计时必须成对。

| 指标 | 被 game 的方式 | 配对指标 |
|:---|:---|:---|
| 引用密度 | 每句话贴引用，包括无关的 | 引用相关性（judge 抽检） |
| 覆盖率 | 子问题拆得极细，每个答一句 | 每个子问题的证据条数中位数 |
| 召回率 | 放宽检索式，全都召回 | 诱饵召回率 |
| 精确率 | 收紧到只留最相关的 1 篇 | 核心文献召回率 |
| 报告长度 | 灌水 | 引用密度（引用数 / 字数） |
| 无证据声明率 | 什么都声明证据不足 | 常规题上的覆盖率 |

最后一行值得注意：F4（静默降级）的对策是要求声明缺口，但过度声明会让系统
变成"什么都答不了"。所以 S2 类安全 case 必须和常规 case 一起看。

## 八、分层运行

自动评测的成本必须与触发频率匹配，否则要么跑不起，要么没人跑。

| 层 | 内容 | 耗时 | 成本 | 触发 |
|:---:|:---|:---|:---|:---|
| L1 | 硬约束 + Component 断言 | 秒级 | 0 | 每次提交 |
| L2 | 20 条 E2E + trajectory 统计 | 分钟级 | 有 API 成本 | 每日 / 每次合并 |
| L3 | judge 打分 + 人工采样复核 | 小时级 | 高 | 每个版本 |

L1 必须完全免费且确定 —— 一旦引入模型调用，它就不能当门禁用。本项目的硬约束
全部是集合比对与字符串匹配，满足这个条件。

---

## 九、失败归因分类

跑完不是终点，把失败归类才是。分类必须落到**可修改的位置**上，否则归因没有行动价值。

| 归因 | 修改位置 |
|:---|:---|
| 检索式写歪 | Planner 的 prompt / few-shot |
| 检索式对但源里没有 | 加数据源 / 放宽 OA 限制 |
| 召回了但被 Ranker 误杀 | Ranker 的打分标准 / 阈值 |
| 召回了但全文拿不到 | Reader 的降级策略 |
| 全文有但没抽出证据 | Extract 的 prompt |
| 抽出了但没写进报告 | Synthesis 的 prompt |
| 写了但论断超范围 | Review 的检查项 |

这张表的每一行对应本项目的一个节点。**workflow 形状的归因优势在此** ——
失败能定位到具体节点；agent 形状只能看 trajectory 猜。这是选型时容易被忽略
的一项成本。

## 十、这套设计不能回答什么

**综述的学术质量。** 所有硬约束通过、召回率精确率都好看，产出的仍可能是一份
组织混乱、重点错位的综述。学术质量只有领域专家能判断，且判断本身有分歧。
这套评测能保证的是"没有编造、没有遗漏声明、覆盖了提出的子问题"，保证不了
"这是一份好综述"。

**跨题可比性。** 不同问题的文献密度差一个数量级，同一套指标在不同题上的绝对值
不可比。只能同题跨版本比。

**长期漂移。** 文献库在增长，同一个问题半年后的正确答案会变。金标准需要定期
重标，否则召回率的下降可能来自标注过期而非系统退化。

**判定器本身的正确性。** 硬约束依赖 quote 是全文子串这一假设 —— 若 Reader
的截断策略改变，同一条 quote 可能因为落在截断边界外而被判为不实。判定逻辑与
被测系统存在耦合，改动 Reader 时必须同步检查这条约束是否仍然成立。
